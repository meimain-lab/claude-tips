# 侧边面板交互升级方案（0.3.0）

对象：`pane/`（插件名 `tips-pane`，当前 0.2.0，已推送）。菜单栏应用不在范围内。

先读这三份，它们继续有效：
- [implementation-plan.md](implementation-plan.md) 第 2 节（硬性约束）和第 5 节（视觉规范）。
- [pane-redesign-plan.md](pane-redesign-plan.md) 第 7 节：桌面应用里各元素的真实表现，上一轮试画得出的结论。不要重做这些试验。
- 动手前加载 `plugin-authoring` skill。

## 1. 要做的五件事

### 1.1 两行都能点
- 现状：只有中文说明那一行能触发填入，点英文原文没有反应。
- 改成：英文原文那一行也是一个 `Button`（`plain`），和中文那一行触发同一个动作。每个 `Button` 有自己的 `key`。
- 已知代价：`Button` 里的文字不认等宽字体，英文会变成普通字体。这一点用户已经同意。英文仍用次要色、`truncate-end`。
- 两行的左边缘要对齐。上一版给英文行加过一层 `paddingLeft` 来对齐，改成 `Button` 后这层要去掉或重调，以截图为准。
- 「未整理」的行同样处理：第二行（描述的第一句）也能点，填入的仍是 `/skill 名`。

### 1.2 能看每条提示的详情
- 每行行尾加一个小的 `Button`（`plain`），点一下在该行下面展开这条提示的中文详情（内容文件里的 `detail`），再点收起。
- 同一时间只展开一行：展开另一行时，前一行自动收起。搜索词变化时全部收起。
- 详情文字：次要色、`footnote` 大小、自动换行（不截断），左边缘和上面两行文字对齐。
- 「未整理」的行：详情显示这个 skill 的完整描述。
- 行尾的状态文字（`已填入`、`已复制`、`已不存在`）和展开按钮同时存在时，状态文字在前。
- 展开按钮用文字符号，不用 emoji；展开和收起两种状态要能看出区别。

### 1.3 搜索框占位文字
- 现状：占位文字「搜一下：画图、定时、交接」在面板里被截成「搜一下：画图、定时、交」。输入框不会随面板变宽。
- 改成一句在约 300pt 宽的面板里也能完整显示的短句，例如「搜索：画图、定时」。以截图为准。

### 1.4 在终端里看一次
- 上一版在终端里的画法只有元素树测试，没有人看过。
- 在一个终端里的 Claude Code 会话加载这个 mod（例如 `claude --plugin-dir <仓库>/pane`），打开面板，看：图标字符块是否等宽，两行文字是否对齐，展开详情是否正常，文字有没有乱。
- 做不到实测就在汇报里写明原因，不要写成已验证。

### 1.5 检查英文原文是否正确
检查对象：`content/tips.json` 和 `content/tips.local.example.json` 里每一条的 `copy`。

逐条检查：
- 语法和拼写正确，读起来是自然的美式口语，只含 ASCII 字符。
- 斜杠命令：确认这个命令在当前安装的 Claude Code 里确实存在、名字拼写一致。带参数的（例如 `/loop 5m check the deploy status`）确认参数写法符合这个命令的用法。
- 中文说明和详情说的事，和这句英文实际会让 Claude 做的事一致。

处理方式：
- 明确的错误（拼错、命令不存在、中英文说的不是一回事）直接改，并在汇报里列出改了什么。
- 只是措辞可以更好的，不要改，在汇报里给出建议，由用户决定。
- 另外只读检查用户本机的 `~/.claude/claude-tips/tips.local.json`：有问题只在汇报里说，不改这个文件，也不要把它的内容抄进仓库。

汇报里附一张表：每条 `copy`、结论（正确 / 已改 / 建议改）、依据。

## 2. 不改的

- 读文件、合并、搜索排序、skill 扫描的逻辑不动，除非上面的功能需要新字段。
- 只允许三类钩子：`session.start`（注册命令）、`command.run`、`ui.render`。`/tips` 不向对话返回文字。不往模型上下文里加任何东西，不注册工具、skill 或 agent。
- 行的整体结构（图标块、两行字、悬停变色、点中后的强调色底）保持 0.2.0 的样子。

## 3. 怎么实测

这些是上一轮踩过的坑，照着做可以少走弯路：

- **开发副本**：用户已经从 GitHub 装了正式版 `tips-pane`，每个新会话都会加载它。实测要用一份改了名字的开发副本（插件名、面板编号、命令名都加 `-dev`，例如 `/tips-dev`），放在本会话的 dev-mods 文件夹里。实测时确认看到的是开发副本，不是正式版。
- **热加载只在一轮结束时发生**。需要重新加载时结束这一轮，最后一行写「reload needed, continue me」，发起会话会让你继续。
- 第一次写 mod 文件时，应用会问用户一次是否启用本会话里写的 mod。这一步只有用户能点。
- **截图**：先找到 Claude 窗口的窗口编号，再用 `screencapture -x -o -l <编号>` 只截这一个窗口。这样别的应用挡在前面也能截到，也不会截到别的窗口的内容。本会话必须显示在某个窗口里才能截到面板；不在的话请用户把它开成独立窗口。
- 同一个面板编号在重新加载后不会重画，换一个编号或改一个状态值才会。
- 一个会话同时开在两个窗口里时，填入只会进其中一个窗口的输入框。这是应用的行为，不是面板的毛病。
- 不要点 macOS 的权限弹窗，不要改系统设置（包括深色和浅色外观）；需要切换外观时请用户自己切。
- 不要动用户的插件配置和 `~/.claude/settings.json`。

## 4. 验收

1. 真实画面：在 Claude 桌面应用里对开发副本截图并自己看过。至少要有：深色窄面板（约 300pt）、一行展开详情的状态、点英文行后的「已填入」状态。浅色和宽面板能截就截。
2. 实测：点中文行和点英文行都能填入；展开、收起、换一行展开都正常；搜索时已展开的行收起；占位文字完整显示。
3. `claude plugin validate pane`、类型检查、`claude plugin test pane` 通过。新增测试覆盖：英文行的按钮触发填入、展开和收起、同一时间只展开一行、「未整理」行的详情是完整描述。
4. `scripts/validate-tips.py` 通过；`swift test --package-path menubar` 仍然通过（不应受影响）。
5. `pane/.claude-plugin/plugin.json` 的版本改成 `0.3.0`。README 里面板的用法说明跟着更新（两行都能点、可以展开详情）。

## 5. 提交

- 在 `main` 上提交，提交信息用英文；本文件随第一个提交进仓库。英文原文的修改单独一个提交。
- 提交前检查 diff：不能有姓名、邮箱、公司名、本机路径。作者名保持仓库里设好的 `meimain-lab`，不要改身份。
- 不要推送。推送和更新用户装的那份面板，由发起会话在用户同意后做。

## 6. 汇报里要有的

- 提交编号放在最前面。
- 每件事做了什么、实测看到了什么、截图放在哪里。
- 英文检查的那张表。
- 没能验证的项目，照实写。
